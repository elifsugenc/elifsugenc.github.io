PROJECT

Traces Together.

why trace matters?
A Living Archive of Website Interactions See the collective archive
SOFTWARE Visual Studio Code, JavaScript,
Git & GitHub
OVERVIEW An experimental archive exploring user presence,
temporary digital traces, and collective data interaction.
01 / THE IDEA

Websites are usually designed to be looked at. You enter, scroll, click, and leave.

But what if visiting a website could leave something behind?

This project treats interaction as material. Every movement, click, pause, and decision becomes part of a temporary digital trace: a record of how someone moved through the website.

The website observes each session as something unique. These traces are collected, translated and eventually turned into an artifact.

The visitor is no longer only viewing the website.

They are contributing to its archive. And that is what makes every trace valuable.
You make the archive different simply by being yourself.
No one moves, pauses, clicks, or explores in exactly the same way you do. Your presence changes the archive, even if all you do is be yourself.

02 / COOL, BUT HOW TO MAKE IT WORK

The system did not appear fully formed. It was built through a series of experiments, failed attempts, small discoveries and many revisions.

The first challenge was simple: how can a website remember the way someone moves through it?

02a / CAPTURING THE MOVEMENT

THE GOAL

The first step was to understand how a visitor moves through the website. The mouse normally disappears without leaving any evidence behind. I wanted to turn that temporary movement into something the website could remember.

x → horizontal position
y → vertical position
t → time

[x, y, t] → [x, y, t] → [x, y, t] → …

SUCCESS 01 — movement could become data.

02b / BUT WHOSE DATA IS THIS

THE PROBLEM

Recording coordinates was not enough. If ten people visited the website, I needed to know which coordinates belonged to which visit.

The solution was to create a unique session ID for every visit.

Conceptually, the data now looked like:
{ sessionId: "unique-session-id", points: […] }
The session ID acts like a temporary label. I do not need to know who the visitor is. I only need the system to understand: these points belong to this visit.

The archive is not about identifying people. It is about distinguishing one interaction from another.

SUCCESS 02 — each visit could become its own trace.

02c / SENDING THE DATA

THE PROBLEM

Mouse movement happens constantly. That means the website can generate many coordinates in a short time. Sending every point individually would mean repeatedly communicating with the backend.

Instead, I grouped points into batches. Rather than sending every point separately, a group of points travels together. Each group has its position in the session.

SUCCESS 03 — large amounts of movement data could be transferred in manageable pieces.

02d / FRONTEND TO BACKEND

The browser is responsible for observing the interaction. The collected data then travels to the backend, where each request is checked and organized by visit, points and completion state.

Each part answers a different question: which visit, what happened, and has the visit ended?

SUCCESS 04 — the website could send structured interaction data to its backend.

02e / KNOWING WHEN IT’S OVER

One of the more difficult questions was surprisingly simple: when is a visit finished?

The website could collect information while someone was there, but it also needed to recognize the final part of that visit.

At first the final session was not appearing where expected. The interaction worked, but the artifact did not appear immediately. A later revision connected the final interaction directly to the archive.

02f / FROM DATA TO ARTIFACT

At this point the system could identify a visit, record its movement, group the data and understand when it had finished.

But raw coordinates were never meant to be the final result. The next step was translation.

The collected session data is passed to the backend, where it is transformed into a PDF. The PDF becomes a visual record of that particular visit.

02g / BUILDING THE ARCHIVE

Generating the document was not enough. It also needed somewhere to live. Each completed session is connected to its PDF and stored so individual visits become part of a larger collection.

VISITOR → INTERACTION → DATA → SESSION → PDF → ARCHIVE

The archive therefore does not contain documents I designed individually. It contains documents generated by the people who visited the website.
